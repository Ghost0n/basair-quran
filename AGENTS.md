# Project Repository Instructions

This file defines repository-level instructions for AI coding agents.
Its scope is the entire repository rooted here.

If project-specific assistant files are added later, they should import or defer to this file so this remains the shared source of truth.

## Project Parameters

- `PROJECT_NAME`: `Q-Basair`

Use `PROJECT_NAME` as the ticket prefix in branch names, commit messages, and PR references.

## Project Boundaries

- `Q-Basair` is a Quranic search and research tool focused on Arabic words, roots, phrases, mushaf-aware search, ayah reading, and strict-context Quran research workflows.
- The FastAPI backend owns Quran database access, normalization, search behavior, suggestions, reader APIs, and research-agent orchestration.
- The Next.js frontend owns the search workspace, results, Mushaf reader, and research chat experience.
- The final strict research response must be grounded only in ayahs returned by Quran search.
- The research agent reads nothing but the Quran: no tafsir, hadith, book, transcript or other corpus enters its prompts, and there is no interpretive (Tafssir) mode. Answers saved by the former experimental explanatory reading still display, with their disclaimer.
- Do not silently treat generated artifacts as source truth. `data/quran.db` is a generated/runtime artifact unless a task explicitly asks to version local data.
- Do not expose private notes, source paths, or debug traces in the user-facing UI unless explicitly requested for a developer/debug surface.

## Working Principles

- Quran text, morphology, roots, and mushaf metadata must remain reproducible from documented inputs.
- Search behavior should be deterministic where possible, especially normalization, root matching, phrase search, ayah references, and highlighting.
- LLM behavior must be constrained by explicit prompts, structured outputs, fallback behavior, and tests.
- The research agent's answers come from the Quran alone. Do not add another source, corpus or interpretive mode to it.
- The UI should preserve Arabic readability, RTL layout, and clear distinction between evidence, answer, and experimental interpretation.
- Runtime behavior that affects search results, ayah selection, or research-agent output must be documented and tested.

## Data Rules

- `data/quran.db` is generated by `scripts/build_db.py`.
- `data/translations.db` is generated by `scripts/build_translations.py` from the trusted sources in `scripts/translation_sources.json` (QuranEnc first, Tanzil for gaps). Translations are displayed verbatim with attribution and never enter research-agent context.
- `apps/web/lib/quran-divisions.generated.ts` (juz / hizb / quarter starts) is generated by `scripts/build_quran_divisions.py` and committed (small data the web ships); `python scripts/build_quran_divisions.py --check` (and `tests/test_quran_divisions.py`) re-verify it against `data/quran-narrations/hafs.json`.
- `data/recitations/` holds the prepared recitations (one MP3 + verse timings per reciter and surah, `catalog.json`), generated by `scripts/build_recitations.py` from the sources in `scripts/recitation_sources.json` (Quran.com, mp3quran.net, everyayah.com) and served by nginx (`docs/recitation-audio.md`). A runtime artifact: never committed.
- `data/cache.db` is the shared server cache (derived data computed once and served to every user — today verse audio durations, `src/app/services/recitation_cache_service.py`). A runtime artifact: never user data, never committed, safe to delete (it refills on demand). Prefer adding shared, deterministic, expensive-to-compute data here (with immutable HTTP caching once complete) over recomputing it per user or per device. Caching layers, rules (never mark a per-user route `public` — the nginx edge cache would serve it to everyone) and the latest audit: `docs/caching.md`.
- `build/offline/` is generated by `scripts/build_offline_packs.py` (core database + downloadable packs for the standalone app); it is never committed. In production the deploy builds it into `data/offline/` (`QBASAIR_OFFLINE_PACKS_PATH`) from the server's own `quran.db` and `translations.db`.
- The standalone Android and iOS app is `apps/web` built with `NEXT_PUBLIC_APP_MODE=1` (`pnpm --filter @q-basair/web build:app`, see `docs/offline-app.md`); app-only code lives in `apps/web/lib/app-mode/` and `apps/web/features/app-mode/`, and must leave the web build unchanged.
- `packages/offline-engine` is the TypeScript port of the Quran routes for the standalone app. Changing Quran search/reader behaviour or `src/app/models/api.py` means porting the change there too: regenerate `src/models.generated.ts` (`python scripts/generate_offline_models.py`) and keep the parity suite green (`docs/offline-engine.md`).
- Prefer committing source code, scripts, tests, docs, and `.gitkeep` placeholders. Do not commit generated DBs or large local corpora unless the user explicitly asks for local data to be versioned.
- If local data is committed intentionally, keep it in a dedicated commit and mention size/contents in the close-out.
- The code is AGPL-3.0 (`LICENSE`); third-party data and fonts keep their own terms, listed in `NOTICE.md`. A new data source, font or media file must be added there with its source and terms in the same change, and nothing whose terms forbid redistribution is committed (fetch it at build/deploy time instead). Going-public steps and settings: `docs/open-source.md`.

## Research Agent Rules

The agent answers from the Quran alone (`src/app/services/research_agent_service.py`):

- Term discovery uses only the question and the Quran's own vocabulary (roots and words from `quran.db`); no book, transcript, tafsir or other corpus is read.
- Use the LLM to produce search terms, then execute searches through existing Quran search logic.
- Generate the final answer only from the selected ayahs (each read with its neighbouring ayahs from `quran.db`), references, matched terms and Quran search results. The prompt (`QURAN_ONLY_ANSWER_RULES`) forbids tafsir, hadith, scholars' opinions, rulings and outside knowledge, and requires saying when the ayahs do not answer.
- Keep displayed ayah cards synchronized with the final kept ayah IDs from the backend.
- If structured JSON parsing fails, fall back to plain answer behavior rather than breaking the chat.
- `response_mode` / `tafssir_depth` are still accepted from older clients and ignored; the response's `tafssir` and `disclaimer` stay null. Answers saved by the former explanatory reading keep displaying with their disclaimer.

### Local troubleshooting

- **The reader (or any screen) shows a 500 / "تعذّر إتمام الطلب"**: this almost
  always means the FastAPI backend isn't running. The Next server only proxies
  `/api/*` to it (`QBASAIR_API_ORIGIN`, default `http://127.0.0.1:8001`), so a
  dead backend surfaces as a 500 through the proxy — it is **not** a code
  regression. Fix: restart the API (`python scripts\start_api.py`), confirm
  `GET /api/health` returns 200, then reload the page. The local API is a plain
  process, not a service — it can stop between sessions.
- **Accounts, sign-in, the account menu, or the Community sign-in prompts are all missing**:
  the web must be **built** with `NEXT_PUBLIC_AUTH_ENABLED=1` (it's baked at build
  time). Without it the app runs single-user/local with no account concept.
  Pair it with a backend started with `QBASAIR_AUTH_ENABLED=1`.
- Raw technical error strings are never shown to users — see
  `docs/error-reporting.md` (sanitized messages + the scaffolded report pipeline).

## Git Workflow

### Branch Naming

Use the following format for branch names when the user does not request a specific branch:

`type/{PROJECT_NAME}-<next-number>-description-courte`

Rules:

- Use one of the approved branch types.
- Use the project ticket id in the branch name, prefixed with `Q-Basair`.
- Write the description in lowercase kebab-case.
- Do not use brackets in branch names.

Approved branch types:

- `feat`
- `fix`
- `hotfix`
- `chore`
- `docs`
- `release`

Example:

- `feat/Q-Basair-124-recherche-tafssir`

### Commit Naming

Use the following default commit message format:

`type: [{PROJECT_NAME}-<next-number>] - Message clair`

Rules:

- On branches other than `develop` and `main`, derive the bracket token from the current branch name first.
- If the branch name follows `type/{PROJECT_NAME}-7-description-courte`, use `[{PROJECT_NAME}-7]` in commit messages on that branch.
- If no ticket number is present in the branch name, fall back to `[{PROJECT_NAME}-<branch-name-without-type/>]`.
- On `develop` and `main`, use `[<branch_name>-<next-number>] - Message clair`.
- Start with `feat`, `fix`, `chore`, `docs`, `hotfix`, `release`, `refactor`, or `test`.
- Include the derived branch token in brackets.
- Use an imperative verb.
- Keep the message precise and concise.
- Keep one commit focused on one logical change.

Examples:

- `feat: [Q-Basair-124] - Ajoute la recherche tafssir`
- `fix: [Q-Basair-125] - Corrige la normalisation des racines`
- `docs: [Q-Basair-126] - Documente le corpus de recherche`
- `docs: [Q-Basair-7] - Ajoute les instructions agents`
- `docs: [Q-Basair-research_agent] - Ajoute les instructions agents`

### Pull Requests

PRs should follow these rules:

- One PR should cover one logical change.
- The title should follow the project ticket convention.
- The description should include context, implementation summary, tests, and any known limitations.

PR title format:

`[Q-Basair-<next-number>] short clear summary`

Example:

- `[Q-Basair-124] add structured Tafssir research depth`

If the current branch has no ticket number, use `{PROJECT_NAME}-<branch-name-without-type/>` as the PR token as well.

## Continuous Deployment

Production is one Contabo VPS serving `basairquran.com` (full guide: `docs/deployment.md`). `.github/workflows/release.yml` runs on every push or merge to `main`:

1. Builds the `api` and `web` images on GitHub's runners and scans them with Trivy (a CRITICAL or HIGH finding that has a fix stops the release; accepted exceptions go in `.trivyignore` with their reason).
2. Pushes them to GitHub Container Registry (`ghcr.io/ghost0n/basair-quran-{api,web}:<commit>`).
3. Copies the deploy files to `/srv/q-basair` over SSH and runs `deploy/server/deploy.sh --tag <commit>`: pull, restart, the data jobs named by the deploy tags, then a readiness gate on `/api/ready` reporting that commit — the previous release is put back if it fails.

Every pull request also runs `.github/workflows/ci.yml`: tests, builds, offline-engine parity, nginx/compose checks, a Trivy scan of the repository, and a Sonar analysis once `SONAR_TOKEN` is set. Keep both green; never weaken a scan to pass it.

### Deploy tags

Append one or both tags to the commit message on `main` when a rebuild is needed:

| Tag | When to use |
|---|---|
| `[rebuild-db]` | `scripts/build_db.py` changed, or Quran source data changed |
| `[rebuild-translations]` | `scripts/build_translations.py` or `scripts/translation_sources.json` changed (runs in the background; also runs when `data/translations.db` is missing) |
| `[prepare-recitations]` | `scripts/build_recitations.py` or `scripts/recitation_sources.json` changed, or to prepare more reciters (background, resumable; which reciters: `QBASAIR_PREPARE_RECITERS`, default `configured`) |
| `[prefill-recitation]` | the reciter catalogue changed, or to complete the shared recitation-duration cache (`scripts/prefill_recitation_cache.py`, background, resumable; also runs when `data/cache.db` is missing) |

Examples:

```text
feat: [Q-Basair-130] - Modifie le schéma de la base [rebuild-db]
feat: [Q-Basair-131] - Ajoute une source de traduction [rebuild-translations]
feat: [Q-Basair-132] - Migration complète [rebuild-db] [rebuild-translations]
```

Without a tag the deploy only swaps the images (a few minutes). Redeploy or roll back by running the Release workflow by hand with `image_tag`, or on the server with `./deploy/server/deploy.sh --rollback`.

### Agent guidance on deploy tags

When proposing a commit that touches any of the following, include the relevant tag in the suggested commit message:

- `scripts/build_db.py`, `scripts/build_morphology.py`, or any Quran source file → `[rebuild-db]`
- `scripts/build_translations.py` or `scripts/translation_sources.json` → `[rebuild-translations]`
- `src/app/services/reciter_service.py` (reciter catalogue) → `[prefill-recitation]`
- `scripts/build_recitations.py` or `scripts/recitation_sources.json` → `[prepare-recitations]`

Do not add tags for changes that only touch Python application code, frontend code, tests, or documentation — those do not require a database rebuild.

### Server and secrets

The server is prepared once with `deploy/server/setup.sh`; the release workflow logs in as the `deploy` user with the `DEPLOY_*` secrets of the `production` environment. `.env.production` lives at `/srv/q-basair/.env.production`, is never committed, and is the only place for production secrets. See `docs/deployment.md`.

## Optional CI Skip Tag For Minor Meta Commits

For small metadata-only commits on feature branches, you may use:


Use this only for tiny documentation or metadata changes. Do not use it for code, API, search, database, or research-agent behavior changes.
